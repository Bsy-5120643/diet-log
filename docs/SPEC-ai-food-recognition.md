>
> 功能描述、数据结构、UI 交互、API 设计、错误处理、成本控制、
> 隐私与授权、模型选型均已确认。

## 1. 背景与目标

用户手动搜索食物录入成本高，尤其在吃「宫保鸡丁盖饭」这类复合菜品时，
需要自己拆成鸡胸肉、花生、米饭、食用油分别记录，几乎不可用。

目标：用户拍一张照片 → AI 自动识别菜品并拆解成食材 → 用户确认/微调份量 → 一键记入当日饮食。

**明确的非目标**：
- 不做医疗级营养分析，不接受「误差必须小于 5%」这类要求
- 不做连续拍照 / 视频流识别
- 不做条形码识别（与拍照识别是两条独立路径）

## 2. 功能描述（已确认）

识别输出采用 **C 方案：菜品名 + 食材拆解 + 总营养**。

拍一张「宫保鸡丁盖饭」照片，系统返回：

- **上层**：菜品名「宫保鸡丁盖饭」+ 估算总热量「约 550 kcal」
- **下层（默认折叠）**：拆解出的食材明细，每项带克数
  ```
  鸡胸肉    120 g    142 kcal
  花生米     20 g    120 kcal
  米饭      200 g    232 kcal
  食用油     10 g     90 kcal
  --------------------------------
  合计               约 584 kcal
  ```

### 2.1 「临时菜品」机制（已确认）

AI 识别成功后，动态创建一条菜品记录存入库中，而不是用完即弃。

这样做的理由：
- 用户修正过克数后，下次拍同一道菜可以复用
- 同一餐可以反复添加（比如吃了两碗）
- 为后续「菜品库运营」留出空间

### 2.2 总热量的计算口径（重要）

**总热量必须由食材明细累加得出，不接受 AI 直接给的总数。**

理由：AI 直接输出的「约 550 kcal」是黑盒，一旦用户把花生从 20g 改成 10g，
总数就对不上了。必须由 `Σ(每 100g 营养值 × 克数 / 100)` 现算，才能保证
「改任意一项 → 总数实时正确」。

AI 可以给一个总热量作为**参考展示**，但落库和计算一律以明细累加为准。

## 3. 数据结构（已确认）

### 3.1 新增 `recipes`（菜品表）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | uuid | 主键 |
| `user_id` | uuid NOT NULL | FK → users，级联删除。**菜品归用户私有** |
| `name` | varchar(200) | 展示用菜品名，如「宫保鸡丁盖饭」。用户可在确认页改名 |
| `normalized_name` | varchar(200) | **归一化名**，用于去重匹配。见 3.5 |
| `total_energy_kcal` | numeric(8,2) | 冗余总热量，由明细累加，**可被重算覆盖** |
| `source` | varchar(16) | `ai` / `manual` / `seed` |
| `is_temporary` | boolean | AI 生成的临时菜品，默认 true；用户保存后置 false |
| `origin` | varchar(16) | `user`（用户私有）/ `public`（公共库，为 C 方案预留） |
| `created_at` / `updated_at` | timestamptz | |

索引：
- **`(user_id, normalized_name)` 唯一** —— 「同名直接复用」的实现基础

**架构确认：本项目不引入任何对象存储（OSS / S3 / R2 等）。**
图片只在内存中流转，用完即弃，`recipes` 表不设 `photo_url` 字段（第 5 轮已确认）。

> **一处与原始设想的偏差，需要说明**
> 你提到唯一索引建在 `(user_id, recipe_name)`。我建在 **`(user_id, normalized_name)`**。
> 原因：如果建在原始名上，「宫保鸡丁」和「宫保鸡丁盖饭」会被当成两道不同的菜，
> 复用逻辑直接失效——而这正是选 A 方案的核心收益。
> 归一化名就是把两者统一成「宫保鸡丁」后的那个键。

### 3.2 菜品名归一化规则（重点）

目标：把「宫保鸡丁盖饭」「自制宫保鸡丁」「四川宫保鸡丁（微辣）」统一成 **宫保鸡丁**。

#### 归一化步骤

```
输入: AI 给出的菜品名
  │
  ├─ 1. 基础清洗
  │     去首尾空白、去全部内部空白
  │     去全角/半角标点
  │     去括号及内容：（微辣）(小份)【】[]
  │
  ├─ 2. 剥离前缀（来源 / 地域 / 修饰，不改变菜品本体）
  │     自制 家常 妈妈 私房 招牌 秘制 正宗 特色 手工 传统 经典
  │     台湾 四川 广东 湖南 北京 上海 日式 韩式 泰式 意式
  │
  ├─ 3. 剥离后缀（盛放形式 / 规格，≥2 字）
  │     盖浇饭 盖码饭 盖饭 盖浇 套餐 便当 定食 拼盘 双拼 三拼
  │     一份 中份 大份 小份 例份 加饭 配饭
  │
  └─ 4. 输出 normalized_name
```

#### ⚠️ 关键约束：不做单字剥离

**不剥离「饭 / 面 / 粉 / 汤 / 锅」这类单字，也不剥离「炒饭 / 拌面 / 汤面」。**

反例说明为什么：

| 输入 | 若剥离 | 结果 | 判断 |
|---|---|---|---|
| 蛋炒饭 | 剥「炒饭」 | **蛋** | ❌ 荒谬 |
| 葱油拌面 | 剥「拌面」 | **葱油** | ❌ 变成调料名 |
| 卤肉饭 | 剥「饭」 | **卤肉** | ❌ 变成食材名 |
| 兰州牛肉面 | 剥「面」 | **兰州牛肉** | ❌ 不可辨识 |

所以剥离表只收 **≥2 字且明确表示「容器/规格/份量」** 的词，
凡是可能是菜品本体一部分的一律不动。

#### 匹配策略：先试探，不激进

归一化不只是「存的时候剥一层」，而是**匹配优先**：

```
1. 用清洗后的原名去查 (user_id, 原名)  → 命中则复用
2. 不命中 → 依次尝试各条剥离规则，每剥一次查一次 → 命中则复用
3. 都不命中 → 当作新菜品，normalized_name = 清洗后应用规则剥离的结果（保守剥离，见上）
```

这样即使规则不完美，也只会「多建一条菜」，不会「把两道菜错误合并」。

#### 逃生口

1. **用户可手动改名**：确认界面提供菜名输入框，用户改完即作为新的 `normalized_name`
   （说明：改名后下次以新名为准）
2. **「重新识别」按钮**：见 4.3

### 3.3 新增 `recipe_ingredients`（菜品食材明细）

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | uuid | 主键 |
| `recipe_id` | uuid | FK → recipes，级联删除 |
| `food_id` | uuid | FK → foods（**复用现有食材库，不新建营养数据**） |

**关键点**：`food_id` 指向现有 `foods` 表，营养值永远从 `foods` 读。

这样食物成分表修正后，所有菜品的热量自动跟着更新，不存在两份数据打架。

## 4. UI 交互（已确认）

### 4.1 默认状态（折叠）

```
┌────────────────────────────────────┐
│ 🍜 宫保鸡丁盖饭          约 584 kcal │
│    [展开明细 ▾]      [调整] [记入午餐]│
└────────────────────────────────────┘
```

- 只显示菜品名 + 总热量，不吓唬用户
- 「展开明细」是二级入口，只给想校核的用户

### 4.2 展开状态

```
鸡胸肉       [ 120 ] g    142 kcal
花生米       [  20 ] g    120 kcal      ← 可直接改
米饭         [ 200 ] g    232 kcal
食用油       [  10 ] g     90 kcal
────────────────────────────────────
合计                     584 kcal
```

交互规则：
1. 每个食材的克数是**可编辑输入框**
2. 改动任意一项 → 该项热量 + 底部合计**实时重算**（纯前端算，不发请求）
3. 某项删掉（克数改 0 或点删除）→ 从明细移除，合计同步更新
4. 若某食材在 `foods` 里营养数据缺失 → 该项显示「-」，**合计按 0 计入**，
   并提示「有食材缺营养数据」

### 4.3 「重新识别」按钮（必须提供）

确认页保留一个「重新识别」入口，点击后**强制调用 AI 重新识别**，
并用新结果**覆盖**该用户这道菜的记忆（`recipes` + `recipe_ingredients`）。

存在的理由：选了 A 方案（同名复用）后，最大的风险是
「AI 第一次估错了，用户没改，错误被一直复用下去」。

典型场景：用户今天换了家餐厅，同样叫「宫保鸡丁盖饭」，但分量和配比完全不同。

交互细节：
- 按钮位置：确认页菜品名旁边，次级按钮样式（不是主操作）
- **不需要二次确认**：直接重识别即可，因为新结果仍需用户点「保存」才会落库，不存在误覆盖风险
- 但需明确提示「本次将消耗 1 次识别额度」
- 重新识别**会消耗一次配额**（明确告知用户）
- 重新识别后的结果仍走完整的确认流程，用户的克数修改同样会被记住

### 4.4 菜名手动改名

确认页的菜品名是**可编辑输入框**，不是只读文本。

- 默认填入 AI 识别 + 归一化后的名字
- 用户改完 → 保存时以用户填的名字为准
- 改名会生成新的 `normalized_name`，下次以新名匹配
- 若改后的名字与已有菜品冲突（同名）→ 提示「已存在同名菜品，是否合并？」（合并规则见 §10）

### 4.6 警告提示条（已确认）

确认页**顶部**挂一条醒目的黄色提示条，只要 `warnings` 非空就显示。

```
┌────────────────────────────────────────────┐
│ ⚠ 识别结果仅供参考，请核对后再记录           │
│   · 存在未匹配食材：松茸                    │
│   · AI 置信度较低（0.82）                   │
└────────────────────────────────────────────┘
```

交互规则（已确认）：

- **只要用户不点「保存」，就可以随意操作**：改克数、删掉不认识的食材、手动改菜名
- 黄色提示条**不阻断**任何操作，只是提醒
- 用户删除未匹配项后，对应的 warning 应实时从提示条上消失
- 「保存」按钮在存在未匹配食材时**禁用**，并在按钮附近给出原因
  「请先删除或替换带 <未匹配> 的食材」

### 4.7 空态：完全没认出

`ingredients` 为空数组时，确认页不展示空表格，而是展示引导：

```
┌────────────────────────────────────────────┐
│  😕 没能认出这是什么                        │
│     试试：拍清楚一点 / 让食物占满画面        │
│                                            │
│     [重新拍照]   [手动搜索食物]              │
└────────────────────────────────────────────┘
```

「手动搜索食物」跳转到现有的 `/today` 搜索页，保证用户永远有路可走。

### 4.8 实时重算公式（前端与后端必须一致）

```
单项热量 = round(该食材每100g热量 × 克数 / 100, 1)
总热量   = Σ 所有单项热量
```
与后端 `app/services/nutrition.py` 的 `scale()` 保持同一套算法，避免前后端算出两个数。

## 5. 成本控制（已确认）

### 5.1 配额

- 非会员：**每天免费识别 5 次**
- 会员：额度待定，见 §10（付费墙未立项，本期不实现）
- 付费墙：本期**不做**，只留前端展示位与后端校验钩子

**放宽到 5 次的依据**：选了 A 方案（同名直接复用）后，用户拍同一道菜
从第 2 次起就不再消耗 AI 调用。真正消耗配额的只有「新菜品」和「主动点重新识别」，
实际频次远低于「每天吃的顿数」。

### 5.2 计费口径（已确认：**自然日 + 失败不扣**）

**自然日**：按**用户时区**的 0 点重置，不是 UTC。
（沿用项目既有约定，见 `app/core/time.py` 的 `current_local_date()`）

**失败不扣**：下列情况**不消耗配额**：

| 场景 | 是否消耗 |
|---|---|
| 识别成功（含部分成功、含未匹配食材） | ✅ 消耗 1 次 |
| 点「重新识别」 | ✅ 消耗 1 次 |
| 命中已有菜品，直接复用 | ❌ 不消耗 |
| 模型返回「完全没认出」 | ❌ 不消耗 |
| 模型超时 / 不可用（502 / 504） | ❌ 不消耗 |
| 被限流拦截（429） | ❌ 不消耗 |

理由（用户已确认）：大模型难免网络超时或识别失败，失败还扣次数
会让用户觉得被"骗钱"，直接流失。

> 注意：失败不扣 ≠ 可以无限刷。防刷由 §5.4 的限流策略承担，
> 两者职责分离——**配额管成本，限流管滥用**。

### 5.3 配额展示（已确认）

拍照按钮旁实时显示剩余次数：

```
┌──────────────────────────┐
│ 📷 AI识别 (剩余 3 次)     │   ← 正常
└──────────────────────────┘

┌──────────────────────────┐
│ 📷 AI识别 (今日已用完)    │   ← 禁用
└──────────────────────────┘
```

- 数据来源 `GET /api/v1/ai/quota`，进入页面时拉取一次
- 每次识别成功后，用响应里的 `quota` 字段**就地更新**，不再额外发请求
- 次数耗尽 → 按钮禁用 + 文案变化
- 处于锁定状态（见 5.4）→ 显示锁定原因与解锁时间，而非次数

### 5.4 限流与防刷（已确认）

因为「失败不扣配额」会让反复调用变得零成本，必须在 API 层加独立限流。

#### 规则

| 规则 | 阈值 | 处置 |
|---|---|---|
| 分钟级限流 | 同一用户 **每分钟最多 2 次**识别 | 429 `rate_limited` |
| IP 级兜底 | 同一 IP **每分钟最多 10 次** | 429 `rate_limited` |
| 连续失败锁定 | **连续 5 次「完全没认出」** | 锁定 1 小时，429 `temporarily_locked` |

#### 什么算「一次失败」

**只统计「模型成功返回但完全没认出食物」（`ingredients` 为空数组）。**

不计入连续失败的场景：
- 图片格式错（400）—— 输入问题，不是识别失败
- 模型不可用 / 超时（502 / 504）—— 基础设施问题，不该惩罚用户
- 已被限流或配额耗尽的请求 —— 根本没调到模型

这样既能拦住"反复上传垃圾图片刷接口"，又不会因为我们的服务抖动误伤正常用户。

#### 检查顺序（很重要，直接影响成本）

限流必须**在调用模型之前**判断，否则挡不住花钱：

```
1. 是否处于锁定状态 (locked_until > now)  → 429 temporarily_locked
2. 分钟窗口是否超限                        → 429 rate_limited
3. 配额是否用尽                            → 429 quota_exceeded
4. 通过 → 记 minute_count + 1 → 调用模型
5. 按结果回写：
     成功            → quota_used += 1；consecutive_failures = 0
     完全没认出       → consecutive_failures += 1；达到 5 → locked_until = now + 1h
     模型不可用       → 不改配额，不改连续失败计数（但 minute_count 已计）
```

### 5.5 配额与限流的数据结构

新建 `ai_recognition_usage` 表：

| 字段 | 类型 | 说明 |
|---|---|---|
| `user_id` | uuid | FK → users |
| `usage_date` | date | 自然日（用户时区），配额重置维度 |
| `quota_used` | int | 当日已消耗配额（仅成功调用计入） |
| `minute_bucket` | timestamptz | 当前分钟窗口起点（固定窗口法） |
| `minute_count` | int | 该分钟窗口内已发起次数（**无论成败**） |
| `consecutive_failures` | int | 连续「完全没认出」次数 |
| `locked_until` | timestamptz NULL | 锁定截止时间 |
| `updated_at` | timestamptz | |

主键：`(user_id, usage_date)`

> 说明：用固定窗口（minute_bucket）而非滑动窗口，是因为实现简单、
> 单次查询即可判断，对免费层数据库足够。代价是窗口边界可能瞬间放行 2 倍请求——
> 对本场景（2 次/分钟）可接受。

#### ⚠️ 不用 4xx 表达「识别结果不理想」（已确认）

**只要不是协议层或资源层错误，一律返回 `200 OK`，问题放进 `warnings`。**

理由：识别结果不理想是**可恢复的产品状态**，不是协议错误。用 4xx 会逼前端写两套分支，
而实际上用户还能继续操作（改克数、删食材、改名、重拍）。

#### warnings 类型表

| warning | 触发条件 |
|---|---|
| `存在未匹配食材: X` | AI 给出的食材在 `foods` 表里匹配不到 |
| `AI 置信度较低（x.xx）` | 置信度低于阈值（初值 0.7，压测后调整） |
| `图片较模糊` | 图片质量检测结果 |
| `未在图片中识别到食物` | 完全认不出，此时 `ingredients` 为 `[]` |

**「完全认不出」也走 200 + 空数组**，前端展示空态并引导重拍或手动搜索。不占用 4xx。

#### 未匹配食材的处理（已确认）

- 前端展示为 `<未匹配>`，营养列显示 `-`
- **合计按 0 计入**（复用既有的 NULL 兜底逻辑）
- **后端不建占位食材数据** —— 只在用户点保存时提示处理

### 6.2 确认并写入

```
POST /api/v1/ai/confirm
{
  "request_id": "uuid",
  "dish_name": "宫保鸡丁盖饭",
  "entry_date": "2026-10-25",
  "meal_type": "lunch",
  "ingredients": [
    { "food_id": "uuid", "quantity_g": 120 },
    { "food_id": "uuid", "quantity_g": 10 }     // 用户把花生改成 10g
  ],
  "save_as_recipe": true         // 是否保存/更新为自己的菜品
}

200 OK
{
  "entry_group_id": "uuid",
  "recipe_id": "uuid",
  "total_energy_kcal": 514.2,    // 按用户提交的克数重算，非 AI 原始值
  "created_entries": 4
}

400  { "detail": { "code": "unmatched_ingredient",
                   "message": "存在未匹配食材，请先删除或替换" } }
```

**约束**：

1. `confirm` 只接收 **`food_id` 非空**的食材项。
   若请求里含 `food_id: null`，返回 `400 / unmatched_ingredient`。
   —— 与「部分成功」并不矛盾：部分成功指的是**识别阶段**返回结果，
   但**落库阶段**必须干净，不能把没有营养数据的东西写进记录。
   前端应在保存前就拦截并提示用户删除或替换未匹配项。

2. `confirm` 接收的是 `food_id + quantity_g`，**不是算好的热量**。
   热量一律服务端 `scale()` 重算，防止客户端提交任意数值。

## 7. 错误处理（已确认）

### 7.1 总原则

**能返回就返回，能操作就别拦。** 识别质量问题是可恢复状态，不是错误。

只有三类情况才用 HTTP 错误码：

| 场景 | 状态码 | code |
|---|---|---|
| 图片格式不支持 / 体积过大 / 损坏 | 400 | `invalid_image` |
| 配额已用尽 | 429 | `quota_exceeded` |
| 分钟级限流 | 429 | `rate_limited` |
| 连续失败锁定 | 429 | `temporarily_locked` |
| 模型服务不可用 / 超时 | 502 / 504 | `ai_service_unavailable` |

其余一切（未匹配食材、置信度低、图片模糊、完全认不出）**全部 200 + warnings**。

### 7.2 错误码体系

沿用项目既有的统一格式：

```json
{ "detail": { "code": "quota_exceeded", "message": "今日识别次数已用完" } }
```

前端按 `code` 分支，`message` 直接展示给用户。

### 7.3 各失败场景的产品表现

| 场景 | 接口表现 | 前端表现 |
|---|---|---|
| 完全没认出 | 200 + `ingredients: []` | 空态引导；**不扣配额**，但计入连续失败 |
| 部分食材未匹配 | 200 + warning | 该项显示 `<未匹配>`，营养 `-`，合计按 0 |
| 置信度低 | 200 + warning | 黄色提示条，不阻断 |
| 图片模糊 | 200 + warning | 黄色提示条建议重拍（不强制） |
| 图片格式错 | 400 | 提示「不支持的图片格式」 |
| 配额用尽 | 429 `quota_exceeded` | 按钮显示「今日已用完」+ 引导 |
| 模型超时 | 502 / 504 | 「网络超时，请重试」+ 手动搜索；**不扣配额**；**后端不存临时文件** |
| 网络错误 | 前端捕获 | 同上 |
| 保存时含未匹配项 | 400 `unmatched_ingredient` | 前端提前拦截，理论上看不到 |

### 7.4 降级路径（关键）

**任何一步失败，用户都必须有路走到「手动记录」。**

```
拍照失败 / 识别失败 / 服务不可用
        │
        ▼
  [手动搜索食物] ──▶ 跳转 /today 现有搜索页
```

这条路径必须存在，否则功能失败 = 用户记录中断，对饮食记录类 App 是硬伤。

## 8. 隐私与数据存储（已确认）

### 8.1 图片不落盘（已确认：**完全不存，用完即弃**）

```
用户拍照
   │
   ├─ 图片进入后端内存（仅存在于请求生命周期内）
   │
   ├─ 转发给模型厂商做识别
   │
   ├─ 拿到识别结果
   │
   └─ 请求结束，图片随内存释放 —— 不写磁盘、不写数据库、不写对象存储
```

明确约束：

- **不引入任何对象存储**（OSS / S3 / R2 / Supabase Storage）
- `recipes` 表**不设 `photo_url` 字段**（已从表结构中移除）
- 数据库中只保存识别结果：菜品名、食材、`food_id`、克数
- 无临时文件、无清理任务——因为根本没有文件产生

### 8.2 隐私告知文案（已确认）

在**拍照按钮旁**或**首次授权相机的弹窗**上，用极小的灰字展示：

> **图片仅用于 AI 识别分析，识别后即销毁，不会保存在服务器中**

要求：

| 项 | 规范 |
|---|---|
| 位置 | 拍照按钮下方，或首次相机授权弹窗内 |
| 样式 | 极小号、灰色（弱化视觉，但不隐藏） |
| 时机 | 用户在**点拍照之前**就能看到，不能事后才告知 |

目的（用户已确认）：极大降低用户防备心，同时满足隐私合规的**最底线要求**——
即「处理前告知」。

### 8.3 传输失败的处置（已确认）

**传给模型厂商过程中若发生网络超时 / 失败：直接把错误抛给前端，
后端绝对不要在本地存临时文件。**

```
模型调用超时
   │
   ├─ 不重试落盘，不写临时文件，不排队
   │
   ├─ 返回 502 / 504
   │
   └─ 前端提示「网络超时，请重试」+ 手动搜索入口
```

理由：一旦为了「重试」而把图片落盘，就违背了 8.1「不落盘」的承诺，
隐私声明也就站不住脚了。**宁可让用户重拍一次，也不破例存图。**

同时（与 §5.2 一致）：这类失败**不扣配额**，且**不计入连续失败锁定**。

### 8.4 授权方式（已确认：**B 方案 + 常驻灰字**）

**首次使用时弹一次明示同意弹窗，之后不再弹**；
同时保留 §8.2 的常驻灰字。MVP 阶段**不做**设置页开关（D 方案）。

#### 弹窗内容

```
┌────────────────────────────────────────────┐
│  AI 拍照识别需要你的同意                     │
│                                            │
│  · 照片会发送给 AI 服务商用于识别菜品        │
│  · 识别完成后立即销毁，我们不保存图片        │
│  · 只会保留识别出的菜品名、食材和克数        │
│                                            │
│         [ 取消 ]      [ 同意并继续 ]        │
└────────────────────────────────────────────┘
```

#### 数据结构

**不单独建「同意记录表」**，直接在 `users` 表加一个布尔字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `has_agreed_ai_privacy` | boolean | 默认 `false`；用户点「同意」后置 `true` |

```sql
ALTER TABLE users
  ADD COLUMN has_agreed_ai_privacy boolean NOT NULL DEFAULT false;
```

#### 交互规则

- 未同意（`false`）时点击拍照 → 先弹同意弹窗，不直接调相机
- 同意后写入 `true`，**同一账号不再重复弹**
- 用户选「取消」→ 不写库，下次点击仍会弹
- 后端 `POST /ai/recognize` 也校验该字段：`false` 时返回 `403 / ai_privacy_not_agreed`
  （前端已拦，后端再拦一层防止绕过）

> **取舍说明**：不建独立的同意记录表是 MVP 阶段的简化——
> 代价是无法追溯「用户同意的是哪个版本的条款」。
> 待条款迭代或监管要求明确后，再升级为
> `user_consents(user_id, doc_type, doc_version, agreed_at)` 这类版本化结构。


## 9. 验收标准

### 9.1 识别与复用

- [ ] 拍一张菜品照片 → 返回菜品名 + 食材明细 + 总热量
- [ ] **总热量 = Σ(每项每100g热量 × 克数 / 100)**，与 AI 直接给的数值无关
- [ ] 拍同一道菜第二次 → 命中缓存（`cache.hit = true`），**不消耗配额**
- [ ] 归一化生效：「宫保鸡丁盖饭」「自制宫保鸡丁」映射到同一条菜品
- [ ] 归一化不误伤：「蛋炒饭」不会被剥成「蛋」，「葱油拌面」不会被剥成「葱油」
- [ ] 点「重新识别」→ 强制调 AI，覆盖该用户这道菜的记忆，并消耗 1 次配额

### 9.2 确认与修改

- [ ] 默认折叠，点「展开明细」才显示食材
- [ ] 修改任一食材克数 → 该项热量与总热量**实时**更新
- [ ] 前后端算出的热量一致（同一套 `scale()` 算法）
- [ ] 确认页菜名可编辑，改名后以新名保存

### 9.3 不确定结果的处理（第 3 轮）

- [ ] 有未匹配食材时，接口仍返回 **200 OK**（不是 4xx）
- [ ] `warnings` 数组正确包含「存在未匹配食材: X」「AI 置信度较低」
- [ ] 前端在确认页顶部显示黄色提示条，列出所有 warning
- [ ] 未匹配项显示 `<未匹配>`，营养列显示 `-`，**合计按 0 计入**
- [ ] 存在未匹配项时「保存」按钮禁用，并说明原因
- [ ] 用户删除未匹配项后，对应 warning 从提示条实时消失，保存按钮恢复可用
- [ ] `confirm` 提交含 `food_id: null` 的项时，后端返回 400 `unmatched_ingredient`
- [ ] 后端**不**为未匹配食材创建占位数据

### 9.4 失败与降级

- [ ] 完全认不出 → 200 + 空数组，前端展示空态（不是报错弹窗）
- [ ] 空态提供「重新拍照」和「手动搜索食物」两个出口
- [ ] 配额用尽 → 429，前端禁用拍照按钮并引导
- [ ] 模型不可用 → 502，提示稍后重试 + 手动搜索入口
- [ ] **任何失败路径都能走到手动搜索**（降级路径必须存在）

### 9.5 数据一致性

- [ ] 每次「记入」产生的 `food_entries` 都带营养快照，事后改 `foods` 不影响历史
- [ ] 同一餐的多条记录共用 `entry_group_id`，可整组删除
- [ ] 记录带 `recipe_id`，可回溯到菜品
- [ ] 非会员第 6 次识别时被拦截（**后端校验**，非仅前端禁用）
- [ ] 拍照按钮旁实时显示「剩余 N 次」
- [ ] 每分钟第 3 次识别被限流拦截（429 `rate_limited`）
- [ ] 连续 5 次「完全没认出」后，功能锁定 1 小时（429 `temporarily_locked`）
- [ ] 模型超时**不扣配额**（配额计数不变）
- [ ] 限流判断发生在调用模型之前（不产生费用）
- [ ] `recipes` 表**没有** `photo_url` 字段
- [ ] 项目**未引入**任何对象存储 SDK
- [ ] 拍照按钮旁可见灰字「图片仅用于 AI 识别分析，识别后即销毁，不会保存在服务器中」
- [ ] 模型调用超时时，后端**不产生任何临时文件**（可通过监控磁盘 / 临时目录验证）
- [ ] 超时提示为「网络超时，请重试」，且提供手动搜索入口

## 12. 模型选型（已确认：**境内模型**）

### 12.1 决策

**首选：阿里云通义千问 VL（Qwen-VL 系列）；备选：智谱 GLM-4V。**
明确**不采用**境外模型（GPT-4o / Claude 等）。

### 12.2 理由

1. **数据出境合规**：国内运营，图片若传给境外服务商会触发数据出境相关合规要求，
   风险与成本都显著更高。境内模型数据不出境，合规路径简单。
2. **网络稳定性**：境外 API 在国内访问延迟高且经常不可用，直接影响识别成功率
   （而「失败不扣配额」意味着失败成本由我们承担）。
3. **识别准确率足够**：国产多模态模型对中文菜品——尤其是盖浇饭、麻辣烫、
   中式快餐这类复合餐食——的识别准确率已能满足需求。
4. **生态与成本**：本项目部署在阿里云生态上，接入通义千问 API 链路最短、成本最低。

### 12.3 对 SPEC 其他章节的影响

| 章节 | 影响 |
|---|---|
| §8.2 隐私告知 | 无需写「图片将传输至境外服务商」，文案更简洁 |
| §8 合规清单 | 不触发数据出境相关条目 |
| §8.4 同意弹窗 | 弹窗中「AI 服务商」指境内厂商，可具名 |

### 12.4 接入方式

- 通过官方 SDK 调用，图片以 **base64 或内存字节流**形式传入
- **不写临时文件**，与 §8.1「不落盘」一致
- 超时时间：初值 15 秒，压测后调整（见 §10）
- 返回结果统一收敛成 §6.1 定义的响应体，屏蔽厂商差异

### 关于 AI 拍照识别功能

**我们如何处理你的照片**

当你使用「AI 拍照识别」功能时，你拍摄的照片会被发送到我们合作的**境内** AI
服务商（阿里云通义千问），用于分析图片中的食物。

**照片不会被保存。** 识别完成后，照片会立即从系统中销毁。我们：

- 不会把照片保存在服务器上
- 不会把照片存入数据库
- 不会使用任何云存储服务留存照片
- 不会将照片用于识别以外的任何用途

**我们会保留什么**

我们只保留识别的**结果**，不包括照片本身：

- 识别出的菜品名称
- 拆解出的食材及其克数
- 由食材计算出的热量与营养素

这些数据与你手动记录饮食时产生的数据性质完全相同，用于为你生成每日营养汇总。

**你的控制**

- 首次使用该功能前，我们会征求你的同意
- 你可以随时选择不使用该功能，改用手动搜索记录——功能完全等价
- 你记录的饮食数据可在应用内删除

**关于第三方**

我们仅将上述照片提供给提供 AI 识别能力的服务商，用于完成一次识别。
该服务商位于中国境内，我们不会将你的照片传输至境外。

**联系我们**

如你对本说明有任何疑问，可通过应用内的反馈入口联系我们。
